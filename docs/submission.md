# Devpost submission

**Project name:** Pantry Pilot

**Tagline (<=60 chars):** Shift, donation and volunteer triage for small pantries

**Track:** Good Neighbor Agents

**Try it out:** https://dmwmur6m6t.us-east-1.awsapprunner.com (coordinator console on AWS App Runner; the swarm runs on Amazon Bedrock AgentCore Runtime `arn:aws:bedrock-agentcore:us-east-1:796330847946:runtime/PantryPilot_PantryPilotAgent-YouoNt9rM6`)

**Code:** https://github.com/ritwikareddykancharla/pantry-pilot

## Inspiration

Small food pantries run on one or two volunteer coordinators. Their evenings go to texting for Saturday cover after two cancellations, remembering who is trained on intake, telling a donor when to bring 40 lbs of rice, and noticing diapers are almost out. None of it is hard; it is relentless and it happens on a phone at 9pm. Coordinator burnout is one of the main reasons small pantries shrink. We wanted an assistant that does the routine part and asks the coordinator only when a person needs to decide.

## What it does

Pantry Pilot reads the inbound message queue (volunteers, donors, partner organisations) and runs a daily checklist seven days ahead. On its own it answers schedule questions, processes cancellations and finds a fair replacement (skills, availability, fewest recent shifts), logs donations and proposes drop-off windows inside open hours, sends day-before reminders, flags below-par and expiring stock, and drafts a donor ask. It escalates when two volunteers want the same slot, when a donation may not fit in the freezer, when a minor needs a supervisor, and before any broadcast or purchase over the threshold. Escalations arrive in a console as cards with two or three options and a recommendation; the coordinator taps one and the reply flows back to the agents as an ordinary message. Each cycle ends with a structured weekly brief.

## How we built it

- **Strands Agents Swarm**: three specialist agents (`dispatcher`, `roster`, `steward`) with `handoff_to_agent`, `max_handoffs=12`, repetitive-handoff detection, and a shared `FileSessionManager` (S3 when deployed).
- **Strands tools**: 24 `@tool` functions with precise docstrings over a small SQLite `Store`; tools read `agent.state` for the cycle id and the approval flag.
- **Strands hooks**: an `AuditHook` on `AfterToolCallEvent` records every call with `event.agent.name`, which gives the console its handoff trail and activity feed.
- **Structured output**: `WeeklyBrief` (Pydantic) via `Agent(..., structured_output_model=WeeklyBrief)`.
- **Amazon Bedrock**: `BedrockModel` with Claude Sonnet 4.6 (`global.anthropic.claude-sonnet-4-6`).
- **Amazon Bedrock AgentCore Runtime**: `main.py` uses `BedrockAgentCoreApp` with a single `invoke` entrypoint dispatching `sweep`, `inbound`, `decide`, `ask`, `status`; the FastAPI console can run against the deployed runtime with `AGENT_BACKEND=agentcore`.
- **FastAPI + vanilla JS** coordinator console, `sqlite3` store, `uv`, `ruff`, `pytest` with a deterministic scripted model so the whole suite runs offline.

## Challenges

Making human-in-the-loop conversational rather than modal: no interrupts, no approval queue that blocks the swarm. We settled on an `escalate_to_coordinator` tool that only writes a decision row, and a `decide` path that turns the coordinator's tap into an inbound message the swarm reads on its next cycle. Gated actions needed a second trick: the tool stores its exact payload, and on approval we call the same tool directly on an agent whose state carries `approved=True`, so nothing is re-generated by the model. Testing a Swarm without model access meant writing a Bedrock-shaped scripted model, including the forced-tool path that structured output relies on.

## Accomplishments

A complete, offline-testable multi-agent product: 33 tests in under 20 seconds, a live console where a simulated text is handled within seconds with a visible dispatcher -> roster -> steward trail, and an audit trail that names the agent for every action.

## What we learned

Fairness rules and safety rules belong in code (`ranking.py`, `org.yaml`), not in the prompt; the model should call `find_candidates` and get a ranked list rather than reason about who worked last. Computed facts plus model prose is a better brief than model-computed numbers.

## What's next

Real connectors (Twilio SMS/WhatsApp inbound and outbound, Google Sheets or Airtable roster import), a DynamoDB `Store`, AgentCore Memory for volunteer preferences across cycles, Spanish-language replies, and a volunteer-facing "my shifts" text command.
